# Document support (docx, xlsx, pptx, pdf)

Design notes and decisions, so the work can be continued from any commit. What a person must check by hand in real
Office applications is in [documents-compatibility.md](documents-compatibility.md).

## Clean-room

Everything here is designed from ECMA-376 (OOXML), ISO 32000 (PDF), Microsoft's open specification [MS-DOCX] (for the
Word 2013+ comment parts) and the documentation of the libraries we link.
Anthropic's `docx`, `pdf`, `pptx` and `xlsx` skills were not read, fetched or adapted, and must not be: their license
forbids copying and derivative works. All fixtures are generated by our own Go code from the specifications.

## Layout

| Where | What |
|---|---|
| `packages/client/documents` | The format code: no dependency on the tools or the session. Pure Go except the optional engine. |
| `packages/client/tools/document.go` | `DocumentRead` and `DocumentEdit`: read-before-write, rewind snapshot, atomic write, verification report. |
| `packages/client/server/sessiondiff_documents.go` | Semantic diff of documents in the Changes pane, on the disk and git paths. |
| `packages/client/skills/builtin_documents.md` | The `documents` skill, in our own words, embedded in the client and loaded only for judgement work. |
| `packages/core/prompts/tools/Document*` | Tool descriptions and schemas. |

## Tools

Two built-in tools, because built-in schemas cost tokens every session and one tool per operation would be about twenty:

- `DocumentRead` (`structure`, `read`, `search`, `check`, `render`, `fields`, `ocr`): read-only, in the read-tool permission list.
- `DocumentEdit` (`edit`, `create`, `merge`, `split`, `convert`): in the edit-tool permission list.

Two tools rather than one because permission rules, plan mode and accept-edits all work per tool name.

Every write has one target, `file_path`, so the permission check sees the whole effect. That is why `split` writes one
output per call, and why `merge`/`split` sources must have been read first (reading them passed the read check).

## Tiers

- **Pure Go, always there:** reading, search, editing, package and format checks, form filling, page operations, creation.
  Builds keep `CGO_ENABLED=0`.
- **Optional engine:** rendering, and recalculation of formulas beyond the built-in evaluator. When something is missing the
  tool says "not available" and the check counts as "could not verify"; it never reports a pass.

### Engine choice

- **LibreOffice found on the machine** (`soffice` on PATH or in the usual install places) converts Office files to PDF and
  recalculates workbooks. It is a separate process we never link, so its MPL license does not reach us. It runs on a
  temporary copy, with its own profile directory, macros off and link updates off. Tests that start the real program are
  behind `HARNESS_TEST_LIBREOFFICE=1`; by default they use a fake script, so a test run never launches it.
- **LibreOffice does not run under the macOS sandbox.** Traced under the Seatbelt profile of `sandbox/seatbelt.go`
  (LibreOffice from Homebrew's cask, November 2026): it aborts at start (SIGABRT, `abort() called`), denied the Mach
  services `com.apple.windowserver.active`, `com.apple.coreservices.launchservicesd`, `com.apple.tccd.system`,
  `com.apple.pasteboard.1`, `com.apple.distributed_notifications@Uv3`, then `com.apple.CARenderServer`, plus
  `file-issue-extension`. Allowing the window server alone still aborts; allowing LaunchServices alone hung for over three
  minutes and was stopped. We did not widen the profile: LaunchServices is exactly what lets a process start things
  outside the sandbox. Each failed launch also leaves a crash report, and one was followed by a plain `soffice` under
  launchd, so the engine must not even try.
  **Decision:** with the sandbox active on macOS the engine reports "not available" without starting anything. A call may
  pass `run_outside_sandbox`, which goes through the same user-only prompt as Bash's (`PermissionHints`, checked as a
  `soffice` command, and a policy can refuse it); then it runs unconfined, on a temporary copy with its own profile. With
  the sandbox off it runs as any local program would. Reads, edits and format checks do not need it. Where a future
  platform has a sandbox driver, the engine runs under it through `Engine.Confine`, untested there.
- **PDFium through WebAssembly** (`github.com/klippa-app/go-pdfium` MIT, PDFium Apache-2.0/BSD, `wazero` Apache-2.0)
  rasterises PDF pages without CGO. It is embedded, so PDF pages render even without LibreOffice. The first start
  compiles the module (about 20 s on an M-series Mac); the compiled code is cached under the user's cache directory, so
  later starts are fast. It only ever starts for a `render`.
- Rejected: Poppler (GPL) and MuPDF (AGPL) cannot be linked. `pdfcpu` (already a dependency, Apache-2.0) does the page and form work.

## Addressing

An address is an ID plus an 8-hex content fingerprint, both from `structure`, `read` or `search`:

| Format | ID | Fingerprint covers |
|---|---|---|
| docx | `document:p12`, `header1:p0`, `footnotes:p3`: story part and ordinal of the paragraph | the paragraph's XML bytes |
| docx rows | `document:t1/r2`: the table's ordinal in its story (nested tables count, in document order) and the row's | the row's XML bytes |
| docx pictures | the paragraph's address plus `position`, 1-based among the pictures of the paragraph | the paragraph's XML bytes |
| xlsx | `Sheet1!B2` | the cell's XML bytes (an empty cell has a fixed value) |
| pptx | `s256/sp4`: the slide's `sldId` (survives reordering) and the shape's `cNvPr` id | the shape's XML bytes |
| pdf | page numbers; form fields by full name | not needed: page operations are whole-file and refuse on any change since read |

Rules:

- Batch edits resolve every target against the file as it is, then apply together: no address shifts inside a batch.
- A fingerprint mismatch is refused with the current text and fingerprint, unless exactly one paragraph or shape of the
  same story now has that fingerprint (an earlier insert shifted the ordinal): then it is followed and reported.
- More than one match, for a `find` or a fingerprint, is refused with the candidates.
- The tool also goes through read-before-write tracking: the file must have been read and not changed since.

## Editing

Only the parts that change are rewritten: other zip entries are copied with `zip.Writer.Copy`, compressed bytes and
headers intact, in their order. Inside a changed part only the changed element's bytes are spliced, as `tools/notebook.go`
does, so XML the code does not understand survives. We never round-trip through a library.

Writes are atomic (temp file in the same directory, fsync, rename). Zip limits: entry count, total and per-part
uncompressed size, compression ratio, enforced on the real bytes rather than the declared sizes. DOCTYPE is refused.

The rewind snapshot must succeed first: `Env.BeforeEditChecked` returns the error of `FileHistory.TrackEditChecked` and
the edit is refused. `FileHistory` writes backups and restores files atomically now, for all tools.

## Verification

Runs automatically on a temporary copy, before the user's file is replaced. Findings are compared with those of the
original by a stable key and fall into three states: **new**, **inherited**, **could not verify**. New errors refuse the
edit; new warnings are reported with the written file. Each report says a passing check does not prove Office opens the
file. Rendering runs only on request.

## Decisions per format

See the operation list in the tool description (`packages/core/prompts/tools/DocumentEdit/description.md`).

- docx, mixed formatting: replaced text inherits the formatting of the first run the match touches; when the matched runs
  differ, the report says so. A match may not cross a hyperlink, field or tracked-change boundary.
- docx, tracked changes: an edit is tracked when `w:trackRevisions` is set in the document's settings, unless the call says
  `track: false`; `track: true` forces it. Addresses and text use the view with insertions shown and deletions hidden
  (deleted text is listed separately); `read` marks both.
- xlsx: no row or column insertion in this version. Editing the master of a shared formula, array formulas, merged
  non-anchor cells, table header cells and protected sheets is refused. Strings go in as inline strings, leaving the
  shared-string table alone. Removing a formula also removes `calcChain.xml`, which Excel rebuilds. `fullCalcOnLoad` is
  set when a formula input changes, and dependents get computed values when the built-in evaluator can compute them.
- pptx: slide add, delete and move are atomic. A cloned slide shares layouts and media, loses its notes, and deep-copies
  charts and embedded objects, with a warning.
- pdf: page operations, form fields, and text and pictures added on top of pages. XFA, signed and encrypted files are
  reported and refused. Flat-form overlay is later.

### Pictures (docx, pptx)

- The tool reads the picture file, not the format code: `image` must be an absolute path inside the session's working
  folders or scratch directory, and the read deny rules apply (the permission check saw `file_path`, not the picture).
  PNG, JPEG and GIF only: what Word, PowerPoint and PDF viewers all show. Limits: 50 MB, 60 megapixels.
- Every picture gets a new media part (`word/media/imageN.ext`, `ppt/media/imageN.ext`), a relationship from the part
  that shows it (a header gets its own `.rels` part when it has none) and a `Default` content type for its extension.
  A media part is never overwritten, so replacing a picture another slide or a clone shares leaves that one alone.
- Replacing swaps the relationship of the `a:blip` and drops its extension list (it can hold an SVG copy of the old
  picture that newer Office would show instead), its crop and any link. The old relationship goes when nothing in the
  part uses it any more, and the old media part when no relationship in the package leads to it.
- Sizes: given `cx` and `cy`, or one of them with the picture's own aspect, or its own size at its resolution (pHYs,
  JFIF density, else 96 dpi) shrunk to fit the text area (docx: the last section's page minus margins) or the slide. A
  replacement fits inside the old frame, centred on slides, unless `cx` or `cy` says otherwise.
- docx: a new picture is inline, in a new paragraph after the target or in the target after `find`; with `x` and `y` it
  floats, anchored to the page. The `wp`, `a`, `pic` and `r` namespaces are declared on the new element itself, so the
  file's root is not touched, and Strict documents get Strict namespaces. Drawing ids (`wp:docPr id`) stay unique.
  Tracked replacement deletes the old run and inserts a copy with the new picture (both media parts stay until the
  change is resolved); it needs the picture to have its run to itself. Alt text and size are not tracked, as in Word.
- A missing `alt` is reported, not refused; `alt: ""` marks a picture decorative.

### Table rows (docx)

- New rows copy the target row: row properties without tracked marks, the header flag and conditional formatting;
  each cell's properties without `vMerge`; the first paragraph's properties and first run's format. Cells take values
  split by tabs, rows by newlines; fewer values leave cells empty, more are refused.
- Vertical merges are left to Word: a row is not inserted where the following row continues a merge, the top of a
  merge that continues is not deleted, and rows in a merge are not moved.
- Tracked: an inserted row gets `w:ins` in `w:trPr`, its runs and paragraph marks too; a deleted row gets `w:del` in
  `w:trPr` and its text becomes deleted runs. Accepting or rejecting such a change removes the row or its mark (this
  used to be refused). Moves are never tracked; with tracking on, `move_row` needs `track: false`.
- The last row of a table is not deleted.

### Comment threads (docx)

- ECMA-376 comments are flat. Threads and the resolved flag live in Word's `commentsExtended` part ([MS-DOCX], `w15`):
  one `commentEx` per comment, keyed by the `w14:paraId` of the comment's last paragraph, with `paraIdParent` and
  `done`. We read it, show threads and state in `structure` and `read comments`, and write it.
- `reply_comment` adds a comment whose entry points at the thread's first comment (a reply to a reply answers the
  thread, as Word does) and puts its range and reference next to the parent's. A comment without a `paraId` gets one;
  the comments part then declares `w14` on its root. `commentsExtended` is created, with its relationship and content
  type, when a file has none.
- `resolve_comment` and `reopen_comment` set `done` on the thread's first comment and every reply.
- `delete_comment` deletes the replies with the comment, and their entries.
- Word 2016's `commentsIds` and `commentsExtensible` get entries for new comments only when the file has those parts;
  files without them stay without them. Ids are 8 hex digits below 0x80000000, derived from the batch so a retry gives
  the same ones, and never one the document already uses.
- `mc:Ignorable` is not added for `w14` on the comments root. Word 2010 and later read `w14` natively; Word 2007 would
  not. Recorded here in case a file from an old Word fails.

### Adding to PDF pages

- `add_text` and `add_image` go through pdfcpu: it parses and writes the file and builds the image XObject (JPEG passes
  through as DCT, others are re-encoded with Flate and a soft mask for alpha). The page gets two new content streams
  around its own, `q` before and `Q` plus our drawing after, so the page's own content is not rewritten and whatever
  graphics state it leaves cannot shift what we add. Resources are added to the page's own dictionary; an inherited or
  shared one is copied for the page rather than changed for all.
- Positions are points from the top-left corner of the page as shown: the crop box, after `/Rotate`. A matrix maps
  that to the page's space, so a rotated page takes coordinates the way a reader sees it. Checked by rendering with
  PDFium at 0, 90, 180 and 270 degrees (`TestRealPDFPicturePlacement`).
- Text is the standard Helvetica with WinAnsiEncoding: Latin-1 plus the typographic marks of 0x80-0x9F (dashes, curly
  quotes, euro). Other characters are refused rather than drawn wrong; embedding a font for them is later. Text
  extraction now reads those codes as WinAnsi too, where Latin-1 had only control characters.
- Pictures get no alternative text: the file has no structure tree to hold it, and the report says so.
- The whole file is rewritten by pdfcpu, as for the other page operations. An incremental update would keep the
  original bytes; pdfcpu's `WriteIncrement` was not tried.

### Conversion

- `DocumentEdit` `convert` writes `file_path` from `source` through LibreOffice: docx, pptx and xlsx to PDF, docx to
  ODT, ODT to docx and PDF. It runs on a temporary copy with the engine's private profile, like `render`.
- Under the macOS sandbox it does not start (see Engine choice). With `run_outside_sandbox` the call is checked as the
  `soffice` command it amounts to, with the user-only prompt; the command shown names the output folder. Because that
  check replaces the edit check of `file_path`, a conversion outside the sandbox writes only inside the session's
  folders. Without the sandbox, or without that flag, it is an ordinary edit of `file_path`.
- Sources must have been read, except ODT, which `DocumentRead` cannot read: for it the read deny rules alone apply.
- The output is verified like any write. ODT is not a format we read, so it is checked as a package (the `mimetype`
  entry first, `content.xml` well-formed) and the report says its content was not compared.
- Tests use a fake `soffice` that copies prepared files; none starts the real one.

### OCR

The built-in engine is Tesseract 5.5.4 with Leptonica 1.87.0, compiled for WASI and run under wazero
(`documents/ocr_tesseract.go`). `DocumentRead` `ocr` and `documents.OCREngine` stay the seam: `documents.OCR` is
Tesseract unless a test or embedder replaces it, and with no engine the operation says "not available" and points to
rendering, never an empty result that reads as "no text". `structure` says how many pages look scanned and whether
`ocr` can read them.

What the operation does:

- Scanned PDF pages (`pages`, or every page that looks scanned; at most 20 per call) are rendered through PDFium at 300
  dpi; PNG, JPEG and GIF files in the working folders are decoded in Go. Either way the module gets 8-bit grey pixels
  (transparency over white) and nothing else.
- `languages`: `eng` (the default), `rus` or `eng+rus`. Unknown codes are refused before anything is fetched. Two
  languages cost roughly the time of both.
- Each line comes back with Tesseract's line confidence (`92% text`), and the result says how many lines fell below
  60%. The whole answer sits inside `<document-content … trust="untrusted">` like any other document read, so text in
  a picture that looks like an instruction stays data.

#### The module

- `scripts/ocr/build.sh` builds it reproducibly: wasi-sdk 34 (clang 23), Tesseract 5.5.4 and Leptonica 1.87.0, each
  pinned by version and SHA-256 and fetched into a scratch directory (`OCR_WORK`, about 1 GB, removed afterwards).
  Target `wasm32-wasip1`, a reactor (`_initialize`, then exports), `-O2 -msimd128`, no exceptions, no threads.
  Two builds from scratch gave the same SHA-256.
- Left out: Leptonica's image codecs (png, jpeg, tiff, zlib, gif, webp, openjpeg; the host passes pixels), Tesseract's
  legacy engine (`tessdata_fast` is LSTM only), the ScrollView viewer (sockets), libarchive, libcurl and OpenMP.
  `TESSERACT_IMAGEDATA_AS_PIX` keeps line images as pixes, since without a PNG codec Tesseract's default of storing
  them as PNG bytes fails. `wasi_compat.c` stubs `mkstemp`, `tmpfile` and `system`, which Leptonica names on paths the
  module never takes; they fail with `ENOSYS`.
- `ocr_wasm.cpp` is the interface: `ocr_alloc`/`ocr_free`, `ocr_init(langs)`, `ocr_recognize(pixels, w, h, stride,
  dpi)` returning one row per line (confidence, box, text), `ocr_error`. Its only imports are WASI preview 1 and
  `harness.ocr_cancelled`.
- Size: 2.0 MB, 690 KB gzipped. That is small enough to commit and embed: `documents/ocrwasm/tesseract.wasm.gz` with
  its SHA-256 next to it; the client checks the checksum after decompressing. No download or release asset is needed
  for the module. Rebuilding means running the script and committing both files.
- Licenses are listed in `documents/ocrwasm/LICENSES.md` with the Tesseract (Apache-2.0) and Leptonica (BSD-2-Clause)
  texts. The module also contains wasi-libc (Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT, musl parts MIT) and
  libc++/libc++abi (Apache-2.0 WITH LLVM-exception). No GPL or AGPL code.

#### Running it

- Its own wazero runtime, separate from PDFium's, created on first use and kept for the process; compiled code is
  cached under the user cache directory (`harness/ocr/compiled`), as PDFium's is.
- No host files: the trained data is verified in Go and mounted as an in-memory, read-only `/tessdata`; stdout is
  discarded and the first 64 KiB of stderr kept for error messages. No arguments, no environment, and wazero's default
  fake clock and seeded randomness, so the same pixels give the same text (tested).
- Memory is capped at 1 GiB of linear memory; images over 60 megapixels are refused. Linear memory never shrinks, so an
  instance idle for two minutes is dropped.
- Timeout: two minutes per page, and the caller's cancellation. wazero's `CloseOnContextDone` was tried first and
  rejected: it makes compiled code call back into Go at every loop back-edge, and recognition got ten times slower (20 s
  against 2 s of CPU for a page). Instead `ocr_recognize` passes Tesseract an `ETEXT_DESC` whose cancel callback asks
  the host import `harness.ocr_cancelled`, and Tesseract checks it after every word. Layout analysis before the first
  word is not interruptible; it is bounded by the pixel cap. If a page has not stopped 15 s after its deadline the
  caller gets an error and the next page waits behind it (or gives up at its own deadline). A trap (out of memory, a
  crash) or a timeout drops the instance; the next page starts a new one.
- One page runs at a time (`tessTurn`); pages of one call run in order.

#### Trained data

- `tessdata_fast` 4.1.0 (Apache-2.0): `eng` (4,113,088 bytes) and `rus` (3,861,738 bytes), pinned by size and SHA-256
  in `OCRLanguages`. Fetched on first use from the repository's 4.1.0 tag, checked, then cached under
  `harness/ocr/tessdata` in the user cache directory and checked again every time it is read from there. A file that
  does not match is never used. Without a network on first use the call fails and says what it needed.
- Not embedded: 8 MB for two languages would quadruple what OCR adds to the binary, for a feature many sessions never
  use. Adding a language is a line in `OCRLanguages` with its size and checksum.

#### Speed and memory

Measured with `BenchmarkOCRPage` (an A4 page at 300 dpi, 2480×3508, 40 lines of 10-point Go Regular, warm instance) on
an Apple M4 (`HARNESS_TEST_OCR=1 go test -run - -bench OCRPage ./documents`). The machine was shared with heavy
builds (load 15 to 50 on 10 cores), so wall time is not meaningful; CPU time is the process's user plus system time.
The low figure is from a quiet moment, on performance cores; the high ones from a busy machine, where the work lands on
efficiency cores. One core is used: the module has no threads.

| | CPU per page, quiet | CPU per page, busy | Linear memory after the page |
|---|---|---|---|
| English | 2.0 s | 4.4 to 4.8 s | 47 MiB |
| Russian | not measured quiet | 4.8 to 5.1 s | 50 MiB |

On top of the page: the trained data held in Go (4 MB per language), the compiled module, and the page image (8.7 MB
of RGBA plus 8.7 MB grey). Go's own `Sys` was 207 to 271 MiB in the benchmark process, which also holds the test
images. The first use in a process compiles the module: 1.2 to 1.6 s of CPU, cached on disk after that. Loading a
language and recognising one short line takes about 0.15 s of CPU.

#### Tests

- `documents/ocr_tesseract_test.go` renders text with the Go fonts (Latin and Cyrillic), recognises it and checks the
  words: English, Russian, both at once, determinism, a scanned PDF page through PDFium (`HARNESS_TEST_PDFIUM=1` too),
  and the timeout. `tools/document_more_test.go` runs `DocumentRead` `ocr` end to end on a picture of Russian text.
  These need `HARNESS_TEST_OCR=1`: they fetch the trained data once. The checksum, parsing, pixel and language tests
  run always.

#### Evaluation before the build

Evaluation (November 2026), for a pure-Go or WebAssembly engine under a permissive license:

| Candidate | License | Verdict |
|---|---|---|
| Tesseract 5 (C++) + `tessdata_fast` | Apache-2.0, data Apache-2.0 | The best fit on quality and license, but there is no WASI build. The WebAssembly builds (`tesseract-wasm`, BSD-2; `tesseract.js-core`, Apache-2.0) are Emscripten output that expects its JavaScript runtime. |
| `gogosseract` (Tesseract in WebAssembly under wazero) | Apache-2.0 | Proves the approach, but its author no longer maintains it and it breaks with wazero 1.8 and later; we are on wazero 1.12. Adopting it means owning a fork and rebuilding the module with the Emscripten SDK, about 6× slower than native Tesseract by its author's measure. |
| `gosseract` | MIT | CGO bindings to a system Tesseract: our builds keep `CGO_ENABLED=0`. Rejected. |
| `ocrs` (Rust) | MIT or Apache-2.0 code | Its WebAssembly build targets the browser through wasm-bindgen; its models are trained on HierText, CC BY-SA 4.0, and their own license is not stated. Rejected until the model license is clear. |
| PaddleOCR models | Apache-2.0 | Need an ONNX runtime; the Go ones are CGO. Rejected. |
| Anything under GPL or AGPL | | Excluded by the task. |

The first decision was to stop at the interface; the WASI build of Tesseract it named as the next step is what ships
now (above). Tesseract found on the machine as a separate process remains an alternative that was not needed.

## The skill

Built in rather than a `catalog/` plugin: the tool descriptions point to it and it must be there without an install. It is
embedded, ranks below every other source, so a user's own `documents` skill replaces it, and costs only its name and
description, and only once a session touches a document (`paths` in its frontmatter): the listing goes into the first
message, so an unconditional entry would cost every session and change every first request. It stays loadable by name, for
a new file before anything is touched.

## Changes pane

`server/sessiondiff_documents.go` projects both versions with `Document.Project` and diffs the lines. Projection lines hold
no ordinals, so an inserted paragraph is one added line. Limits: `maxDocumentDiffBytes` per file, `maxDocumentDiffLines` per
side. Results go through the existing `diffCache`, since the totals are measured after every tool. A version that cannot be
read shows as binary. No contract changed: hunks carry the header `compared by content`, and `DiffPane.vue` knows the
extensions. Rewind goes through the existing file history.

## Tests

- Fixtures are generated in Go from the specifications (`documents/fixtures_test.go`, `documents/create.go`), never copied.
- A default test run starts no real LibreOffice and no PDFium. `HARNESS_TEST_LIBREOFFICE=1` and `HARNESS_TEST_PDFIUM=1` turn on
  the real ones (`-run Real`). Tools that reach the engine replace `documents.FindSoffice` with a fake.
- `evals/tasks/doc-*` grade with Python's standard library alone and need no model to self-test.
- [documents-compatibility.md](documents-compatibility.md) lists what only a person with Office can check.

## Left for later

- Row and column insertion in sheets (excluded by design), and writing past `MaxXMLNodes`: very large sheets are refused, not streamed.
- docx: tracked moves and rejecting formatting changes are refused and left to Word. Vertical merges are not split or
  joined by row operations. Pictures cannot be deleted on their own (delete their paragraph), cropped or
  given effects; SVG pictures are not added.
- xlsx: data validation is listed but not enforced on written values. Structured references and other workbooks are not traced: the report counts such formulas. The evaluator covers common functions; others report "unknown".
- pptx: charts cannot be added; picture placeholders are not filled (a picture is added as a free shape); shapes in groups cannot be moved. Clones are tested with a chart and a workbook, not SmartArt or media.
- pdf: flat-form overlay; OCR languages beyond English and Russian, handwriting, and layout (columns and tables come back as lines); text outside WinAnsi on pages; alternative text for added
  pictures. Created PDFs hold Latin-1 only.
- Conversion beyond the pairs above, and pages from an engine other than LibreOffice.
