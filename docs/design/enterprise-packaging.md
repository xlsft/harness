# Enterprise packaging and dev containers

Closes two rows of [docs/comparison.md](../comparison.md): "Enterprise offline packaging" and "Dev container guide". The
manuals are [docs/enterprise.md](../enterprise.md) and [docs/devcontainers.md](../devcontainers.md); this page records why
things are the way they are.

Releases ship for macOS only, so macOS is built and tested; Windows gets its template, Linux its folder, and both are
designed in, not built.

## Decisions

- **One schema, everything generated from it.** `packages/client/settings/policy.schema.json` (JSON Schema 2020-12 with an
  `x-harness` extension: the scope of each key, its template value, the preference domain and the registry key) is embedded
  in the client. `internal/policytemplates` generates the profile, the Intune preference file, the Jamf custom schema, ADMX,
  ADML, a `.reg` and `keys.md` into `deploy/mdm`; `scripts/policy-templates.sh` writes them. Tests fail when the committed
  files differ from what the schema generates, when a file in `deploy/mdm` is generated by nothing, when a schema key is a
  name no client source reads, and when the schema's examples, put together as one policy, give the settings loader a
  problem. The generator is Go so the test runs in the client's CI (`deploy/mdm/**` is in its paths) with nothing to install.
- **The schema lists the keys an administrator manages, not every setting.** Settings that are a person's choice (model,
  theme) aren't in it; they still work in a policy file, as before. Adding a key to the schema is the way to put it in the
  templates.
- **Machine keys are a scope of their own.** `serverUrl`, `disableUpdates` and `updateMirrorUrl` configure the installation.
  They are read only from the machine's own sources (`settings.MachineConfig`), never from documents the server delivers: a
  server must not be able to move a client to another server or another source of code. They live in the same files and
  profile as the policy keys, so an administrator has one place.
- **First source wins for URLs; any source turns updates off.** Device management, then `settings.json`, then the drop-ins
  in name order: the order the policy is read in. A restriction in any of them stands, as with the rest of the policy.
- **The app asks its sidecar** (`harness-client config machine --json`) rather than reading the plist and the registry in
  Rust. One reader, tested once; the sidecar is in the bundle anyway.
- **Profile payload: `com.apple.ManagedClient.preferences` with `Forced`.** Every macOS MDM accepts it, and it lands as
  `/Library/Managed Preferences/com.xlsft.harness.plist`, which the client already read. The UUIDs in the template are stable
  (derived from a name) so regenerating doesn't churn; the manual tells admins to replace them. Device scope only: the client
  doesn't read per-user managed preferences.
- **Windows: single values plus one JSON value.** The client read only `Settings` (a JSON string). Group Policy is clumsy for
  JSON, so the reader now also takes a registry value per scalar key, named by its dotted path (`sandbox.enabled`), typed by
  the schema: a boolean or integer is a `REG_DWORD`, a string a `REG_SZ`. Lists and dictionaries stay in `Settings`, which the
  ADMX offers as one text policy. A single value wins over the same key in `Settings`. Values the schema doesn't know are
  ignored. A one-value enum (`disableBypassPermissionsMode: "disable"`) is an on/off policy that writes that string.
- **The installer package installs the app alone into `/Applications`.** A first version staged `Applications/` and
  `Library/` in the payload; with `overwrite-permissions` that would have reset their owner and mode (`/Applications` is
  `root:admin 775`). Now the payload root is the app, `--install-location /Applications`, `BundleIsRelocatable` false so the
  Installer doesn't put it wherever another copy of the bundle id is. A server URL is written by a postinstall script into
  `settings.d/00-server.json`, so the folders above keep their owners.
- **One package per architecture**, like the DMGs. A universal app would make one package possible; until then
  `hostArchitectures` refuses the wrong Mac.
- **The release package carries no server URL.** An organization's URL can't be in a public release. `build-pkg.sh` is the
  same script the release uses, and takes the release's `.app.tar.gz`, so an admin builds a package with their URL without
  rebuilding the app, whose signature, and so its updates, stay the release's.
- **Package signing has its own secrets and levels.** A Developer ID *Installer* certificate is a different certificate from
  the *Application* one; `APPLE_INSTALLER_*` mirrors `APPLE_CERTIFICATE*`. Notarization is attempted only when the app is
  notarized too, because Apple refuses a package with an ad-hoc app inside. Without the secrets the package is unsigned, and
  the release still ships: the same stance as the app's ad-hoc level. Each build reports its level in `pkg-signing.txt`;
  `assemble.sh` requires the two architectures to agree and passes it to the notes.
- **The pkg is built in `build-release.sh`, for pull requests too.** It needs the `.app` and macOS, both of which the
  `desktop` job has; building it on every desktop PR means a broken package shows before a tag.
- **Mirror layout: `latest.json` at the root, one folder per tag.** That is GitHub's own layout (`releases/latest/download/
  latest.json`, `releases/download/<tag>/<file>`) with the prefixes removed, so the same files work, and several releases sit
  side by side. The root `latest.json` has its URLs rewritten into the mirror; the release's own copy stays untouched under its
  tag, where `checksums.txt` covers it.
- **The mirror is trusted with availability only.** `latest.json` isn't signed and needn't be: the app's updater verifies the
  archive against the built-in key, with `requireSignedVersion`, so a version can't be faked; the client reads only a version
  from it and verifies `<tag>/checksums.txt` with the same key, then the archive. The tests serve a mirror with another key's
  signature and broken `latest.json` files.
- **The offline bundle is a script, not a release asset.** The image tarballs are hundreds of megabytes per platform, and only
  organizations without internet need them. `offline-bundle.sh` builds it from a published release (or files already
  downloaded), checks `checksums.txt`, uses cosign when present, and writes `SHA256SUMS` for the copy across.
- **The server-version hint in Settings → About still asks GitHub.** Pointing the browser at a mirror would need CORS on it;
  offline it just stays quiet, which is what it did before.
- **Dev containers: a feature, plus a from-source recipe.** The feature downloads the Linux archive for the container's
  architecture, which releases don't have yet, and says so; the guide shows a build from source meanwhile. It writes
  `/etc/harness/settings.d/00-devcontainer.json` (the client's Linux system folder) and sets `HARNESS_KEYRING=0`. It checks
  `checksums.txt` against the release key only when `minisign` is in the image: a shell script can't verify Ed25519 alone, and
  pulling a verifier from the network would just move the trust. Its copy of the public key is checked against
  `tauri.conf.json` by `scripts/release/test.sh`. `disableUpdates` defaults to true there: a container is rebuilt, not updated.
- **The feature isn't published to a registry.** Publishing to GHCR needs a workflow and package settings; the guide uses it
  by path until then.
- **The sandbox section stays generic.** The Linux driver (Landlock or bubblewrap) is on another branch. The guide describes
  what the client does with a driver that can't apply, which is already true, and names the kinds of kernel features a
  container runtime may withhold.

## What only builds and fakes have seen

- No real MDM. The profile and preference file pass `plutil -lint` and convert to the keys the client reads; the ADMX and ADML
  are well-formed XML whose references resolve, never loaded by Group Policy or Intune; the Jamf schema never uploaded.
- No profile installed: the plist reader is still tested on its JSON unwrapping only.
- The registry reader is tested on `reg query` text, not on Windows.
- The package is built and taken apart (`pkgutil --expand-full`), its postinstall run against a temporary folder; it was never
  installed. Signing and notarizing it never ran: there is no installer certificate.
- The app's mirror path is the Tauri updater against a fake server (the existing update tests now go through
  `mirror_endpoint`); never against a real mirror.
- The dev container feature ran on macOS against a `file://` mirror, outside a container; its GitHub path and its minisign
  check never ran.
- `actionlint` didn't run here (not installed); the workflows were checked as YAML. CI runs it.

## Left

- Linux and Windows releases: client archives make the dev container feature work as is; a Windows MSI or MSIX for Intune.
- A universal macOS app, then one package.
- Publish the dev container feature to GHCR (`devcontainers/action`).
- More keys in the schema as admins ask for them, for example version floors, which neither updater supports yet.
